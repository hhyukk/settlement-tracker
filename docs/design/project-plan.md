## 1. 프로젝트 개요

### 1.1 한 줄 정의

금 투자 일일 정산 수익을 매일 아침 직접 입력하면 계정별·기간별 순수익과 수익률을 은행 거래내역처럼 조회할 수 있는 개인용 모바일 웹 서비스(PWA).

### 1.2 추진 배경

정산 수익은 매일 오전 6\~7시에 확정되지만 자동으로 내려받을 경로가 없어, 실사용자는 스프레드시트에 직접 기록하고 있다. 계정 수가 늘면서 기간별·계정별 집계를 매번 손으로 해야 하는 일이 번거로워졌다. 이 프로젝트는 수기 입력은 그대로 두고 계산과 조회를 시스템이 맡도록 바꾼다 (SRS 2.1).

실사용자는 매일 오전 정산 직후 한 번, 수십 초 동안 서비스를 쓴다 (SRS 3.1). 인증 방식을 비롯한 주요 결정은 이 짧은 아침 사용을 전제로 한다.

### 1.3 목표와 성공 기준

| 목표 | 성공 기준 | 근거 |
|---|---|---|
| 아침 입력이 부담 없이 끝난다 | 홈 화면 진입 후 3번 이하의 조작으로 전 계정의 당일 입력을 마친다 (금액 입력 제외) | NFR-102 |
| 설명 없이 쓸 수 있다 | 실사용자가 운영자의 도움 없이 당일 입력과 기간 조회를 마친다 | SRS 2.2 |
| 화면의 숫자를 믿을 수 있다 | 화면에 보이는 개별 금액의 합이 표시된 합계와 항상 같고, SRS 4.2의 두 계산 예시가 그대로 재현된다 | CAL-13, SRS 4.2 |
| 기다리지 않는다 | 5년치(약 5,000건) 기준으로 목록 조회와 입력 저장이 각각 1초 이내에 끝난다 | NFR-201, NFR-202 |
| 기록을 잃지 않는다 | 데이터베이스가 매일 자동 백업되고 백업본이 30일 이상 보관된다 | NFR-401, NFR-402 |

## 2. 핵심 설계 원칙

SRS 곳곳에 흩어진 결정 근거를 여섯 가지 원칙으로 묶었다. 설계·구현 중 판단이 갈리면 이 원칙을 기준으로 삼는다.

| 원칙 | 내용 | 근거 |
|---|---|---|
| 입력은 사람이, 계산은 시스템이 | 사용자는 정산 내역에 적힌 총수익과 수수료만 입력한다. 순수익·합계·수익률은 시스템이 산출한다 | CAL-01, CAL-02 |
| 저장된 값이 기준이다 | 조회할 때 수수료율을 다시 적용하지 않고 기록에 저장된 값을 그대로 쓴다. 순수익은 계산 로직이 바뀌어도 과거 데이터가 소급 변경되지 않도록 저장한다 | CAL-05, VAL-08, SRS 4.1 |
| 지난 수익률은 바뀌지 않는다 | 기준 시드는 덮어쓰지 않고 이력으로 쌓는다. 수익률은 정산일자에 유효했던 시드로 계산하며, 서로 다른 시드로 산출된 수익률은 더하거나 평균 내지 않는다 | FR-208, CAL-06, CAL-08, CAL-11 |
| 보이는 금액과 합계가 일치한다 | 금액은 소수 2자리로 저장하고 같은 자릿수로 표시한다. 화면에 보이지 않는 자리가 합계를 어긋나게 만들지 않는다 | CON-04, CAL-13, VAL-13 |
| 기억할 자격증명을 두지 않는다 | 아이디·비밀번호 대신 일회용 초대 링크로 기기를 등록한다. 기기를 잃어버리면 서버에서 해당 기기 토큰만 폐기한다 | FR-102, FR-107, FR-109 |
| 확정된 수익만 다룬다 | 시세·평가손익·손실 개념을 두지 않는다. 수익이 없는 날은 기록을 만들지 않는다 | CON-05, CON-08 |

## 3. 사용자와 이용 시나리오

### 3.1 사용자

| 구분 | 인원 | 역할 | 이용 방식 | 근거 |
|---|---|---|---|---|
| 실사용자 | 1명 | 정산 기록 입력·조회 | 매일 오전 정산 직후 휴대폰 홈 화면 아이콘으로 진입한다. 개발자가 아니므로 학습 없이 쓸 수 있어야 한다 | SRS 2.2 |
| 운영자 (본인) | 1명 | 개발·배포·백업, 초대 링크 발급, 기기 토큰 폐기 | 초대 토큰은 운영자 시크릿으로만 호출되는 관리용 엔드포인트로 발급한다 | SRS 2.2, FR-103, FR-109 |

### 3.2 이용 시나리오

화면 사이의 이동은 4.2 메뉴 구성을 따른다.

| ID | 상황 | 흐름 | 화면 · 근거 |
|---|---|---|---|
| S1 | 처음 접속할 때 | 운영자가 초대 링크 발급(발급 후 1시간, 1회 유효) → 문자 등으로 전달 → 실사용자가 기본 브라우저로 열기 → 토큰 검증 후 기기 토큰을 쿠키로 발급 → 안내에 따라 홈 화면에 추가 | SCR-01 · FR-103\~111 |
| S2 | 매일 아침 입력할 때 | 정산 확인 → 홈 화면 아이콘으로 진입(로그인 절차 없음) → 일괄 입력 → 계정별 총수익 입력 → 미리 채워진 수수료를 정산 내역과 비교해 다르면 수정 → 순수익 확인 → 저장 | SCR-02, SCR-03 · FR-108, FR-303, FR-303-1, FR-309 |
| S3 | 계정마다 정산 시각이 다른 날 | 먼저 나온 계정만 입력하고 저장(빈칸인 계정은 기록을 만들지 않음) → 나중에 다시 들어오면 입력한 계정은 저장값과 함께 완료로 표시되고 남은 계정만 입력 | SCR-03 · FR-310, FR-310-1 |
| S4 | 지난 기록을 고치거나 빠진 날을 채울 때 | 거래내역에서 기록을 눌러 단건 수정·삭제, 또는 단건 입력 화면에서 과거 날짜로 입력 | SCR-03-1, SCR-04 · FR-305, FR-307, FR-308, FR-311 |
| S5 | 지난 기간을 돌아볼 때 | 거래내역에서 기간 프리셋과 계정 선택 → 구간 합계와 누적 순수익 확인 → 통계에서 월별·계정별·시드 구간별 수익률 확인 | SCR-04, SCR-05 · FR-401\~408, FR-502, FR-503, FR-507\~509 |
| S6 | 원금을 넣거나 뺀 날 | 계정 관리 → 시드 이력 → 변경 후 시드 금액과 적용 시작일(보통 입금일) 등록 → 이후 수익률은 새 시드로 계산되고 이전 구간의 수익률은 그대로 유지 | SCR-06-1 · FR-207\~209 |
| S7 | 휴대폰을 잃어버리거나 바꿨을 때 | 운영자가 기존 기기 토큰 폐기 → 새 초대 링크 발급 → S1 반복 | FR-109, FR-110 |

## 4. 서비스 범위

### 4.1 기능 범위

우선순위는 SRS 표기를 따르며, MVP 범위는 M 항목 전체다.

| 기능 영역 | MVP (M) | MVP 이후 (S) | 선택 (C) |
|---|---|---|---|
| 인증 | 초대 토큰 발급·교환, 기기 토큰 발급·갱신·폐기, 권한 없음 안내, 홈 화면 추가 안내 (FR-101\~111) | 로그아웃 (FR-112) | — |
| 계정 관리 | 계정 등록·목록·수정·비활성, 시드 변경 등록과 이력 조회 (FR-201\~209) | 시드 이력 수정·삭제 (FR-210) | — |
| 정산 입력 | 일괄 입력(부분 입력, 당일 재진입 표시), 수수료 제안과 순수익 미리보기, 단건 입력·소급 입력·수정·삭제, 중복·미래 날짜 차단 (FR-301\~311, FR-303-2 제외) | 수수료 이상치 경고 (FR-303-2), 미입력 계정 표시 (FR-312) | 수정·삭제 이력 보관 (FR-313) |
| 조회 | 목록과 정렬 전환, 기간 직접 지정·프리셋, 계정별·통합 조회, 구간 합계, 누적 순수익, 분할 조회 (FR-401\~408) | 금액 범위 검색, 메모 검색, 조회 결과 CSV (FR-409\~411) | — |
| 집계·통계 | 이번 달 순수익과 전월 동기 대비, 월별·계정별 집계, 시드 구간별 수익률, 통합 수익률 (FR-501\~503, FR-507\~509) | 일평균 순수익, 월별 추이 그래프, 시드와 누적 순수익의 합 (FR-504, FR-505, FR-510) | 연도별 집계 (FR-506) |

> 운용 계정이 2개뿐이므로 MVP에서는 두 계정을 초기 데이터로 넣고, 계정 등록 화면(FR-201)은 최소한으로만 구현한다 (SRS 3.2).

> 전체 데이터 CSV 내보내기(NFR-403)는 MVP에서 제외한다. 이관이 없어 오픈 시점에는 내보낼 데이터가 없고, 병행 기간에는 스프레드시트가 사용자 측 사본 역할을 한다. 다만 무기한 미루지 않도록, 스프레드시트 기록을 중단하기 전에 제공한다는 조건을 둔다(7.2). 로그아웃(FR-112)도 S이므로 설정 화면(SCR-07)은 MVP 범위에서 빠진다.

### 4.2 메뉴 구성

SRS 6장의 화면 목록을 이동 구조로 배치한 안이다.

```
초대 링크 진입 (SCR-01)  ← 유효한 기기 토큰 없이 들어온 접속
홈 (SCR-02)
├─ 일일 일괄 입력 (SCR-03)
│   └─ 단건 입력/수정 (SCR-03-1)  ← 거래내역에서 기록을 눌러도 진입
├─ 거래내역 (SCR-04)
├─ 통계 (SCR-05)
├─ 계정 관리 (SCR-06)
│   └─ 시드 이력 (SCR-06-1)
└─ 설정 (SCR-07)  ← MVP 제외. 로그아웃(FR-112)과 전체 데이터 CSV(NFR-403) 모두 MVP 이후
```

### 4.3 범위 외

| 항목 | 사유 |
|---|---|
| 외부 API 연동·자동 수집 | 제공 경로가 없어 수기 입력을 전제로 한다 |
| 시세·평가손익·보유 수량 | 확정된 정산 수익만 다룬다 |
| 다중 사용자·권한 관리 | 사용자는 1명이다 |
| 다중 업체 | MVP 이후 확장 대상이다 (CON-02) |
| 세금 계산·신고 자료 | 별도 검토가 필요하다 |
| 기존 스프레드시트 기록 이관 | 옮기지 않기로 확정했고 일괄 등록 기능도 만들지 않는다. 과거 날짜는 단건 소급 입력(FR-305)으로만 넣는다 |
| 푸시 알림 | MVP 이후 검토한다 |
| 다국어·다중 통화 | 필요하지 않다 |

## 5. 추진 방식

### 5.1 진행 단계와 산출물

개발에 들어가기 전에 문서를 먼저 확정하고, 요구사항 정의 → 기획 → 설계(아키텍처, DB, 화면, API) → 구현 순서로 진행한다.

| 단계 | 산출물 | 상태 |
|---|---|---|
| 요구사항 정의 | 요구사항명세서 | v1.3 완료 (2026-10-06). 설계 해석 DI-01, DI-08 반영 |
| 기획 | 프로젝트 기획서 (본 문서) | v0.7 |
| 일정 관리 | WBS | 작성 완료 (2026-10-06). 구글 스프레드시트로 관리 |
| 설계 | 시스템 아키텍처 설계서 | v0.6 (2026-10-06). 설계 해석 10건 처리 확정, 확인 사항 중 Q-03만 1주차 실기기 검증으로 남음 |
| 설계 | DB 설계서 | v0.2 (2026-10-06). 미결 사항 중 DQ-02(초기 데이터 값, CHK-05)만 남음 |
| 설계 | 화면 설계서 | v0.2 (2026-10-06). MVP 화면 8개 |
| 설계 | API 명세서 | v0.3 (2026-10-06). 남은 확인 사항 4건은 MVP 이후 항목 3건과 1주차 인증 검증 1건이라 착수를 막지 않음 |
| 구현 | 소스 코드, 배포 환경 | 다음 단계. 개발 기간 1개월 |
| 오픈·운영 | 운영 절차서 (초대 링크 발급, 기기 토큰 폐기, 백업 복구) | 오픈 전 작성 |

### 5.2 아키텍처 설계에 넘긴 항목

기술 스택과 배포 구성은 설계서 v0.3에서 모두 확정했다. 항목별 결정과 해당 절은 설계서 1.2의 대응표에 있다. 아래 표는 설계가 만족해야 했던 조건으로 남겨 둔다.

| 결정 항목 | 만족해야 할 조건 | 근거 |
|---|---|---|
| 클라이언트 | 홈 화면 설치와 주소창 없는 실행, 360px 폭에서 가로 스크롤 없음, 금액 입력 시 숫자 키패드와 천 단위 구분 기호, 본문 16px·주요 버튼 터치 영역 44×44px 이상 | CON-03, NFR-101, NFR-103\~105 |
| 인증 처리 | 초대 토큰은 32바이트 이상 난수, 초대 토큰과 기기 토큰 모두 해시로만 저장, 기기 토큰은 HttpOnly·Secure·SameSite 쿠키로만 다루고 스크립트가 읽을 수 있는 저장소에 두지 않음 | FR-104, NFR-302, NFR-305 |

## 6. 일정

### 6.1 마일스톤

개발 기간은 1개월이며 주 단위로 나눈다. 세부 작업과 날짜는 WBS를 기준으로 한다. 쓰기(입력·계정·시드)를 먼저 끝내고 읽기(조회·집계)를 뒤에 두어, 조회 화면을 만들 때 이미 검증된 기록으로 계산 결과를 확인할 수 있게 한다.

| 구간 | 목표 | 주요 작업 | 완료 기준 |
|---|---|---|---|
| 착수 전 | 설계 확정 | 시스템 아키텍처 설계, 확인 사항 해소, 무료 티어 가입과 인스턴스 생성, 무료 서브도메인 준비 | 5.2 항목이 모두 결정되고(설계서 v0.3), 인스턴스와 서브도메인이 준비된다 |
| 1주차 | 기반과 인증 | 개발·배포 환경 구성(HTTPS 포함), PWA 기본 설정, 데이터 모델(TradingAccount, AccountSeed, Settlement), 초대 링크·기기 토큰 인증, 권한 없음·홈 화면 추가 안내, 초기 데이터 확정(CHK-05)과 적재 | 배포된 환경에서 실사용자 휴대폰(또는 같은 OS·브라우저)으로 링크 교환 → 홈 화면 추가 → 아이콘 재진입까지 인증이 유지되고, 초기 데이터가 적재된다 |
| 2주차 | 쓰기 | 일괄 입력(부분 입력, 당일 재진입), 단건 입력·수정·삭제, 수수료 제안과 순수익 미리보기, 계정 관리와 시드 이력 화면, 입력 검증 규칙 | SRS 4.2 금액 입력 예시가 재현되고, 검증 규칙(VAL)을 어긴 입력이 원인과 다음 행동을 알려 주는 안내와 함께 거부된다 (NFR-106) |
| 3주차 | 읽기 | 거래내역(기간·프리셋·계정·합계·누적 순수익·분할 조회), 홈 대시보드, 월별·계정별 집계, 시드 구간별·통합 수익률 | SRS 4.2 시드 변경 예시(10.00%, 5.00%)가 재현되고, 화면의 개별 금액 합과 합계가 일치한다 |
| 4주차 | 안정화와 오픈 | PWA 마감 점검, 자동 백업과 오류 로그, 360px 화면 점검, 5,000건 기준 응답 시간 측정, 실사용자 리허설, 오픈 | 백업본으로 복구를 한 번 해 보고, 실사용자가 도움 없이 당일 입력을 마친다 |

### 6.2 일정 조정 원칙

1. S·C 항목은 MVP 일정에 넣지 않는다.
2. 일정이 밀리면 M 항목 중 쓰기(1\~2주차 범위)를 먼저 오픈한다. 기존 기록을 이관하지 않으므로 오픈이 늦어진 기간의 기록을 서비스에 남기려면 단건 소급 입력으로 하나씩 채워야 한다. 쓰기를 먼저 열면 이 부담이 줄고 스프레드시트 대조(7.2)도 일찍 시작할 수 있다. 목록 화면이 없어도 이미 기록이 있는 날짜로 입력하려 하면 기존 기록 수정으로 안내되므로(FR-304) 고칠 수단은 남는다. 실제 기록이 쌓이기 시작하므로 자동 백업(NFR-401)은 쓰기 오픈과 함께 갖춘다.
3. 읽기(3주차 범위)는 쓰기 오픈 뒤에 이어서 배포한다. 합계와 수익률은 저장된 기록으로 조회 시점에 계산하므로(CAL-05, CAL-11) 나중에 붙여도 그동안 쌓인 기록에 그대로 적용된다.

## 7. 오픈과 운영

### 7.1 오픈 준비

| 항목 | 내용 | 근거 |
|---|---|---|
| 초대 링크 리허설 | 실제로 쓸 전달 수단(문자 등)으로 링크를 보내, 인앱 브라우저가 아닌 기본 브라우저로 열리는지와 홈 화면 아이콘으로 다시 들어와도 인증이 유지되는지 확인한다 | FR-111, SRS 3.1 |
| 발급 시점 | 초대 링크는 발급 후 1시간만 유효하므로 실사용자가 바로 열 수 있는 시간에 맞춰 발급한다 | FR-105 |

### 7.2 스프레드시트 병행과 전환

실사용자는 개발 기간에도 스프레드시트 기록을 이어 간다. 기존 기록은 이관하지 않으므로(SRS 7장) 오픈 후 일정 기간은 두 곳에 함께 기록하고, 같은 날짜 구간의 총수익·수수료·순수익 합계를 대조한다. 스프레드시트가 수수료를 20%로 계산해 두었다면 실제 입력한 수수료와 센트 단위로 차이가 날 수 있으므로, 합계가 다르면 수수료부터 비교한다. 대조 결과가 맞으면 스프레드시트 기록을 그만둘 시점을 실사용자와 정한다. 그만두는 순간부터 서비스가 유일한 사본이 되므로, 그 전에 전체 데이터 CSV 내보내기(NFR-403)를 제공한다.

### 7.3 운영 항목

|---|---|---|

MVP 이후(S) 항목은 매일 입력의 정확도에 영향을 주는 것부터 붙인다.

| 순서 | 항목 | 이유 |
|---|---|---|

## 8. 리스크와 대응

| ID | 리스크 | 영향 | 대응 |
|---|---|---|---|

| R-08 | 무료 티어 인스턴스가 유휴로 판정돼 회수되거나, 무료 서브도메인 서비스에 장애가 난다 | 아침 입력 시간에 앱이 열리지 않는다. 서브도메인을 바꾸면 홈 화면 앱과 기기 토큰을 초대부터 다시 등록해야 한다 | 메모리를 필요한 만큼만 잡아 유휴 판정 조건을 피하고, 종량제 전환과 예산 알림을 둔다. 서브도메인은 공개 접미사 목록에 오른 서비스에서 받는다. 외부 가용성 점검으로 5분 안에 알고, 백업이 VM 밖에 있어 새 인스턴스에 복구할 수 있으며, 월 1회 백업을 운영자 PC에도 받아 둔다(설계서 12.1, 12.3) |

## 9. 착수 전 확인 사항

기획서를 작성하면서 SRS v1.0에 추가로 확인이 필요해진 항목이다. CHK-01\~04는 요구사항 정의에 해당하므로 확정되면 SRS에도 반영한다. 확정된 항목은 9.2에서 9.1로 옮기고 ID는 재사용하지 않는다.

### 9.1 확정된 항목

## 1. 개요

### 1.1 목적
금 투자 일일 정산 수익을 사용자가 직접 입력하고, 입력된 기록을 은행 거래내역과 유사한 형태로 조회·집계할 수 있는 개인용 웹 서비스의 요구사항을 정의한다.

### 1.2 범위
- 포함: 정산 기록의 입력·수정·삭제, 계정 관리, 기간/계정 기준 조회, 순수익 자동 계산, 집계 통계
- 미포함: 외부 시스템 자동 연동, 실시간 시세, 평가손익, 다중 사용자, 세무 신고 기능

### 1.3 용어 정의

| 용어 | 정의 |
|---|---|
| 정산일자 | 정산 수익이 확정된 날짜. 매일 오전 6\~7시에 확정됨 |
| 오늘 | 한국 시간(Asia/Seoul) 기준의 현재 날짜. 서버가 판정하며 클라이언트는 서버가 준 값을 쓴다 (CON-11) |
| 총수익 | 수수료 차감 전 정산 금액 |
| 수수료 | 총수익에서 차감되는 금액. 정산 내역에 표시된 값을 사용자가 직접 입력한다 |
| 수수료율 | 총수익 대비 수수료 비율. 저장하지 않고 입력값에서 산출하며, 입력란 기본값을 채우는 기준값은 20% |
| 순수익 | 총수익 − 수수료. 실제 수령 금액이며 시스템이 계산한다 |
| 기준 시드 | 해당 계정에 투입한 투자 원금. 수익률 계산의 분모가 됨. 적용 시작일을 갖는 이력으로 관리됨 |
| 시드 구간 | 하나의 기준 시드가 유효한 날짜 범위. 다음 시드 이력의 적용 시작일 전날까지 |
| 수익률 | 구간의 순수익 합계 ÷ 해당 구간에 적용된 기준 시드 |
| 통합 수익률 | 전체 계정을 합산한 수익률. 조회 구간의 날짜마다 (그날의 순수익 합계 ÷ 그날의 유효 시드 합계)를 계산해 더한 값 |
| 유효 시드 합계 | 특정 날짜에 운용 중인 계정들의, 그 날짜에 적용되는 기준 시드의 합. 비활성일자가 없거나 그 날짜 이상인 계정이 대상이다 |
| 계정 | 정산 단위가 되는 투자 계정. 업체에서 발급받아 운용하며, 실사용자는 복수 계정을 보유함 |
| 정산 기록 | 특정 계정의 특정 정산일자에 대한 1건의 입력 데이터 |
| 누적 순수익 | 조회 구간 내에서 정산일자 순으로 누적한 순수익 합계 |

> **용어 주의** — 본 문서에서 "계정"은 항상 **투자 계정**을 가리킨다. 서비스를 이용하는 사람은 "사용자"로만 표기한다. 구현 시에도 도메인 엔티티명은 `TradingAccount`로 두어 인증 계층의 `User`와 충돌하지 않게 한다.

## 2. 시스템 개요

### 2.1 배경
정산 수익은 매일 오전 6\~7시에 확정되지만 자동으로 내려받을 수 있는 경로가 없다. 현재는 스프레드시트로 기록 중이며, 계정 수가 늘면서 기간별·계정별 집계가 번거로워졌다. 수기 입력은 유지하되 계산과 조회를 시스템이 담당한다.

### 2.2 사용자

| 구분 | 설명 |
|---|---|
| 주 사용자 | 1명 (실사용자). 매일 아침 정산 금액을 직접 입력하고 조회함 |
| 개발/운영 | 1명 (본인). 개발·배포·백업 전담 |

주 사용자는 개발자가 아니다. 화면 구성과 입력 흐름은 학습 없이 사용 가능한 수준이어야 한다.

### 2.3 제약사항 및 가정

| ID | 내용 |
|---|---|
| CON-01 | 모든 데이터는 사용자 수기 입력으로만 생성된다. 외부 API·크롤링 연동은 하지 않는다 |
| CON-02 | MVP는 단일 업체 + 복수 계정 구조를 가정한다. 다중 업체는 확장 대상 |
| CON-03 | 클라이언트는 PWA(웹)로 구현하며 모바일 브라우저를 1순위로 한다 |
| CON-04 | 통화는 USD 단일 통화이며 모든 금액의 소수 자릿수는 2자리(센트)로 통일한다 |
| CON-05 | 정산 기록은 확정된 값만 다룬다. 평가손익·현재가 개념은 존재하지 않는다 |
| CON-06 | 개발·운영 인력이 1명이므로 무중단 운영은 요구하지 않는다 |
| CON-07 | 현재 운용 중인 계정은 2개이며, 각 계정마다 정산 수익이 별도로 발생한다. 계정 수는 향후 증감할 수 있으므로 2개로 하드코딩하지 않는다 |
| CON-08 | 정산 수익은 항상 양수다. 손실이 발생하는 날은 존재하지 않으며, 수익이 없는 날은 기록을 생성하지 않는다. 따라서 순수익도 항상 양수이고 누적 순수익은 감소하지 않는다 |
| CON-09 | 총수익에서 차감되는 항목은 수수료뿐이다. 세금 등 별도 차감 항목은 존재하지 않는다 |
| CON-10 | 정산은 요일·공휴일 구분 없이 매일 오전에 발생하는 것으로 가정한다. 따라서 미입력 알림(FR-312)에 휴일 예외를 두지 않으며 공휴일 캘린더 연동도 필요 없다. 수익이 없는 날이 실제로 발생하면 기록을 만들지 않는 것으로 처리한다(CON-08) |
| CON-11 | 모든 날짜 판정의 기준 시간대는 한국 시간(Asia/Seoul)이다. "오늘"·"이번 달"·"최근 7일" 같은 날짜 기준은 서버가 이 시간대로 판정하고, 클라이언트는 서버가 준 값을 표시·전송한다. 서버·데이터베이스·런타임의 기본 시간대에 의존하지 않으며, 테스트를 위해 기준 시각을 바꿔 넣을 수 있어야 한다 |

> **기준 시간대 주의** — 정산 확정 시각이 오전 6\~7시이므로 사용 시간대가 한국 시간 자정 직후 구간에 몰려 있다. 배포 환경이 UTC로 동작하면 한국 시간 오전 9시 전까지 서버의 "오늘"이 전날이 되어, 정산일자 기본값이 전날로 채워지고(FR-302) 실제 당일 날짜는 미래 날짜로 거부된다(FR-306). 어제 기록이 없는 날이면 중복 검사(FR-304)에도 걸리지 않아 하루 밀린 기록이 그대로 저장된다.
>
> 정산일자와 적용 시작일은 날짜 값이므로 시간대 변환 대상이 아니다. 화면·API 전 구간에서 `YYYY-MM-DD` 형식으로만 주고받는다. 생성일시·수정일시는 시각 값이므로 저장 방식과 무관하게 한국 시간으로 표시한다.

## 3. 기능 요구사항

우선순위: **M**(필수, MVP) / **S**(권장, MVP 이후 우선) / **C**(선택)

### 3.1 인증

본 서비스의 사용자는 1명으로 고정되어 있으므로 **회원가입과 로그인 화면을 제공하지 않는다.** 사용자는 아이디나 비밀번호를 보유하지 않으며, 운영자가 발급한 일회용 초대 링크를 기기에서 열고 등록 버튼을 한 번 눌러 기기 토큰을 받는 것으로 인증을 마친다. 이후에는 그 기기에서 앱을 열기만 하면 된다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-101 | 시스템은 유효한 기기 토큰을 가진 요청만 데이터에 접근할 수 있도록 한다 | M |
| FR-102 | 회원가입 화면, 로그인 화면, 비밀번호 관련 기능을 제공하지 않는다. 사용자 계정은 시스템 전체에 1건만 존재한다 | M |
| FR-103 | 운영자는 관리용 엔드포인트를 통해 일회용 초대 토큰을 발급할 수 있다. 이 엔드포인트는 환경변수로 주입된 운영자 시크릿으로만 호출할 수 있다 | M |
| FR-104 | 초대 토큰은 32바이트 이상의 난수로 생성한다. 원문은 발급 응답에서 한 번만 반환하며 서버에는 해시만 보관한다 | M |
| FR-105 | 초대 토큰의 유효기간은 발급 후 1시간이며, 1회 사용되면 즉시 만료 처리한다 | M |
| FR-106 | 운영자는 초대 링크를 시스템 외부 수단으로 사용자에게 전달한다 (문자 등) | M |
| FR-107 | 사용자가 초대 링크를 열면 시스템은 기기 등록 화면을 보여 준다. 사용자가 등록 버튼을 누르면 토큰의 해시 일치, 미사용, 미만료를 검증하고, 통과 시 기기 토큰을 발급해 HttpOnly, Secure 쿠키로 저장한 뒤 교환 성공 화면(FR-111)을 보여 준다. 링크를 여는 것만으로는 토큰을 사용 처리하지 않는다 | M |
| FR-108 | 기기 토큰의 유효기간은 90일이며 접속할 때마다 갱신한다. 유효한 기기 토큰이 있으면 별도 절차 없이 홈 화면으로 진입한다 | M |
| FR-109 | 운영자는 발급된 기기 토큰을 개별적으로 폐기할 수 있다. 기기 분실 시 대응 수단이다 | M |
| FR-110 | 기기 토큰이 없거나 만료·폐기된 상태로 접속하면 오류 화면 대신 "접속 권한이 없습니다. 운영자에게 연락해 새 링크를 받으세요"라는 안내를 표시한다 | M |
| FR-111 | 초대 링크를 인앱 브라우저에서 열면 등록 버튼 대신 기본 브라우저로 다시 열도록 안내하며, 이때는 토큰을 사용 처리하지 않는다. 교환 성공 화면에서는 홈 화면에 추가하도록 안내한다 | M |
| FR-112 | 사용자는 명시적으로 로그아웃할 수 있으며, 로그아웃 시 해당 기기 토큰을 폐기한다 | S |

> **인증 방식 선택 근거** — 실사용자는 매일 오전 정산 직후 1회, 수십 초 단위로 서비스를 사용한다. 이 사용 패턴에서 아이디·비밀번호는 평생 거의 입력되지 않으면서 분실·재발급·잠금 로직만 남긴다. 초대 링크 방식은 사용자가 기억하거나 보관할 자격증명이 없고, 기기 분실 시 서버에서 토큰만 폐기하면 되므로 대응도 단순하다. 기기가 사용자 개인 소유임을 전제로 한다.

> **인앱 브라우저 주의** — 초대 링크를 문자나 메신저로 보내면 인앱 브라우저에서 열리고, 쿠키가 그 브라우저에만 저장된다. 이후 홈 화면 아이콘으로 진입하면 인증되지 않은 상태가 된다. FR-111의 안내가 이 문제를 막는 장치이며, 누락 시 사용자는 앱이 고장 난 것으로 인식한다.

> **등록 버튼을 두는 이유** — 문자와 메신저는 링크 미리보기를 만들려고 링크를 먼저 열어 보기도 한다. 링크를 여는 즉시 토큰을 교환하면 미리보기가 일회용 토큰을 써 버려, 사용자가 링크를 열 때는 이미 사용된 링크가 된다. 그래서 교환은 사용자가 등록 버튼을 누를 때만 한다 (시스템 아키텍처 설계서 DI-01, AD-07).

### 3.2 계정 관리

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-201 | 사용자는 계정을 등록할 수 있다. 등록 항목: 계정명(필수), 최초 기준 시드(필수), 시드 적용 시작일(필수), 메모(선택) | M |
| FR-202 | 사용자는 등록된 계정 목록을 조회할 수 있다 | M |
| FR-203 | 사용자는 계정 정보를 수정할 수 있다. 계정명을 변경하면 과거 기록의 표시 이름도 함께 바뀐다. 계정명은 정산 시점의 사실이 아니라 계정의 현재 라벨이므로 기록에 스냅샷하지 않는다 | M |
| FR-204 | 정산 기록이 있는 계정은 물리적으로 삭제하지 않고 비활성 처리한다. 비활성 계정은 신규 입력 대상에서 제외되며 과거 기록 조회는 유지된다. 비활성 처리 시 시스템이 그 시점의 날짜를 비활성일자로 기록한다. 한 번 비활성화한 계정은 다시 활성화하지 않으며, 같은 계정을 다시 운용하는 경우 새 계정으로 등록한다 | M |
| FR-205 | 정산 기록이 한 건도 없는 계정은 시드 이력과 함께 물리적으로 삭제할 수 있다. 사용자가 삭제한 정산 기록도 기록으로 센다. 기록이 1건 이상 존재했던 계정은 삭제할 수 없고 비활성 처리만 할 수 있다(FR-204) | M |
| FR-206 | 계정의 기본 수수료율은 등록 화면에 노출하지 않으며 생성 시 20%로 설정된다. 이 값은 정산 입력 시 수수료 입력란의 기본값을 계산하는 용도로만 쓰인다 | M |
| FR-207 | 사용자는 기준 시드 변경을 등록할 수 있다. 입력 항목: 변경 후 시드 금액(필수), 적용 시작일(필수, 기본값은 오늘이며 비활성 계정은 비활성일자), 사유 메모(선택). 원금 입출금은 입금일부터 즉시 반영되므로 적용 시작일에는 통상 입금일을 넣는다 | M |
| FR-208 | 기준 시드 변경은 기존 값을 덮어쓰지 않고 새 이력으로 추가된다. 이전 시드 구간의 수익률은 당시 시드 기준으로 유지된다 | M |

> 화면에서 계정을 구분하는 표기는 사용자가 등록 시 입력한 계정명 하나로 통일한다. 별도의 표시용 별칭이나 번호를 두지 않는다. 일괄 입력처럼 폭이 좁은 화면에서는 한 줄로 표시하고 넘치면 말줄임 처리한다.

> 수수료율은 전 계정 공통 20%로 고정되어 있어 계정 등록 항목에서 제외한다. 다만 값 자체는 계정 속성으로 보관한다. 입력란 제안값(FR-303)과 이상치 경고 기준(FR-303-2)에 쓰이며, 기준 요율이 바뀌어도 코드 수정·재배포 없이 이 값만 고치면 된다.

> 현재 계정이 2개뿐이므로 MVP에서는 초기 2건을 시드 데이터로 등록하고, 계정 관리 화면은 목록·수정·비활성만 갖춘 최소 형태로 구현한다. 등록 기능(FR-201)의 화면 완성도는 후순위로 둔다.

## 4. 데이터 요구사항

### 4.1 개념 데이터 모델

```
[사용자] 1 ─── N [계정] ─── 1:N ─── [정산 기록]
                   │
                   └────── 1:N ─── [시드 이력]
```

**계정 (TradingAccount)**

| 속성 | 타입 | 제약 |
|---|---|---|
| id | 식별자 | PK |
| 계정명 | 문자열 | NOT NULL, 사용자 내 유일 |
| 기본 수수료율 | 소수 | NOT NULL, 0.0000 \~ 1.0000, 기본값 0.2000. 화면 입력 항목이 아니며 생성 시 기본값으로 설정됨 |
| 활성 여부 | 불리언 | NOT NULL, 기본값 true |
| 비활성일자 | 날짜 | NULL 허용. 활성 계정은 NULL이며, 비활성 처리 시 시스템이 기록한다 |
| 메모 | 문자열 | NULL 허용 |
| 생성일시 / 수정일시 | 일시 | NOT NULL |

비활성일자는 통합 수익률의 분모를 날짜별로 판정하기 위한 값이다(CAL-10). 활성 여부는 현재 상태만 담고 있어 과거 어느 날짜에 그 계정이 운용 중이었는지를 알 수 없다. 비활성 처리 시점이 오늘이고 정산일자는 오늘 이전만 허용되므로(VAL-03), 그 계정의 모든 정산 기록은 비활성일자 이하의 날짜를 갖는다.

**시드 이력 (AccountSeed)**

| 속성 | 타입 | 제약 |
|---|---|---|
| id | 식별자 | PK |
| 계정 id | 식별자 | FK, NOT NULL |
| 시드 금액 | 금액(USD) | NOT NULL, 0 초과 |
| 적용 시작일 | 날짜 | NOT NULL |
| 사유 메모 | 문자열 | NULL 허용 |
| 생성일시 | 일시 | NOT NULL |
| — | — | UNIQUE (계정 id, 적용 시작일) |

적용 종료일은 저장하지 않고 다음 이력의 적용 시작일에서 유도한다. 종료일을 함께 저장하면 이력 추가 시 두 행을 동시에 갱신해야 하므로 불일치 위험이 생긴다.

모든 금액 컬럼은 십진 고정소수점 `DECIMAL(15, 2)`로 통일한다. 소수 2자리는 CON-04에서 확정된 값이며, 정수부 13자리는 실사용 규모를 크게 상회하는 여유값이다.

**정산 기록 (Settlement)**

| 속성 | 타입 | 제약 |
|---|---|---|
| id | 식별자 | PK |
| 계정 id | 식별자 | FK, NOT NULL |
| 정산일자 | 날짜 | NOT NULL |
| 총수익 | 금액(USD) | NOT NULL |
| 수수료 | 금액(USD) | NOT NULL — 사용자 입력값 |
| 순수익 | 금액(USD) | NOT NULL — 총수익 − 수수료로 산출해 저장 |
| 메모 | 문자열 | NULL 허용 |
| 생성일시 / 수정일시 | 일시 | NOT NULL |
| — | — | UNIQUE (계정 id, 정산일자) |

수수료율은 별도 컬럼으로 저장하지 않는다. 총수익과 수수료가 모두 실제 입력값으로 남아 있어 요율은 필요할 때 두 값에서 산출할 수 있고, 컬럼으로 두면 입력값과 어긋날 여지만 생긴다.

순수익은 총수익과 수수료에서 도출 가능한 값이지만, 계산 로직이 바뀌어도 과거 데이터가 소급 변경되지 않도록 저장한다.

### 4.2 계산 규칙

| ID | 규칙 |
|---|---|
| CAL-01 | 총수익과 수수료는 사용자 입력값이며 시스템이 계산하지 않는다 |
| CAL-02 | 순수익 = 총수익 − 수수료 |
| CAL-03 | 수수료 입력란의 기본값은 총수익 × 계정 기본 수수료율로 계산하고 소수 셋째 자리 이하를 버림해 2자리로 맞춘다. 이 값은 제안일 뿐이며 저장되는 것은 사용자가 확정한 입력값이다 |
| CAL-04 | 금액 계산에는 부동소수점 타입을 사용하지 않는다 (십진 고정소수점 사용) |
| CAL-13 | 저장 자릿수와 화면 표시 자릿수를 다르게 두지 않는다. 화면에 보이는 개별 금액을 더한 값이 화면에 표시된 합계와 반드시 일치해야 한다 |
| CAL-05 | 구간 합계는 개별 기록에 저장된 값의 단순 합으로 산출한다. 합계에 수수료율을 적용해 다시 계산하지 않는다 |
| CAL-06 | 특정 날짜에 적용되는 기준 시드는, 해당 계정의 시드 이력 중 적용 시작일이 그 날짜 이하인 것 가운데 가장 최근 1건이다. 판정 기준은 **정산일자**이며 기록을 입력한 시점이 아니다. 소급 입력한 기록에도 그 정산일자에 유효했던 시드가 적용된다 |
| CAL-07 | 수익률(%) = 시드 구간 내 순수익 합계 ÷ 해당 구간의 기준 시드 × 100. 소수점 셋째 자리에서 반올림해 둘째 자리까지 표시한다 |
| CAL-08 | 계정별 수익률은 조회 구간이 여러 시드 구간에 걸치면 시드 구간 단위로 분할해 각각 계산한다. 서로 다른 시드로 산출된 수익률을 더하거나 평균 내지 않는다. 통합 수익률(CAL-10)과 단일 대표값이 필요한 화면(CAL-09)은 이 규칙의 예외이며, 일자별 수익률을 합산한다 |
| CAL-09 | 일자별 수익률 합산은 조회 구간의 각 날짜에 대해 (당일 순수익 ÷ 당일 적용 시드)를 계산해 더하는 방식이다. 통합 수익률의 기본 계산 방식이며(CAL-10), 계정별 수익률에서도 구간이 여러 시드 구간에 걸치는데 단일 대표값이 필요한 화면이면 이 방식을 쓴다. 어느 경우든 합산값임을 화면에 명시한다 |
| CAL-10 | 통합 수익률(%) = 조회 구간의 각 날짜에 대한 (그날의 전체 순수익 합계 ÷ 그날의 유효 시드 합계)의 총합 × 100. 어떤 날짜의 유효 시드 합계는 비활성일자가 없거나 그 날짜 이상인 계정들의, 그 날짜에 적용되는 기준 시드(CAL-06)를 더한 값이다. 해당 날짜에 적용되는 기준 시드가 없는 계정(첫 시드 적용 시작일 이전)은 그날 합계에서 제외한다. 유효 시드 합계가 0인 날짜는 계산에서 제외한다. 계정별 수익률의 산술평균을 사용하지 않는다 |
| CAL-12 | 일평균 순수익 = 구간 순수익 합계 ÷ 조회 구간의 달력 일수. 정산이 없어 기록이 존재하지 않는 날도 분모에 포함한다. 조회 구간의 종료일이 오늘 이후이면 오늘까지로 잘라 계산한다 |
| CAL-11 | 수익률은 저장하지 않고 조회 시점에 계산한다. 계산에는 항상 그 날짜에 유효했던 시드를 사용하므로, 새 시드 이력을 추가해도 과거 구간의 수익률은 변하지 않는다 |

유효 시드 합계가 바뀌는 날짜는 시드 이력의 적용 시작일과 계정의 비활성일자뿐이다. 그 날짜들로 구간을 잘라 (구간 순수익 합계 ÷ 구간 유효 시드 합계)를 더해도 결과는 날짜 단위로 계산한 값과 같다. 조회 종료일이 오늘 이후여도 잘라 낼 필요는 없다. 기록이 없는 날은 분자가 0이라 합에 영향을 주지 않는다. 달력 일수를 분모로 쓰는 일평균 순수익(CAL-12)과는 다른 점이다.

**시드 변경 예시** — 시드 5,000,000원으로 시작해 7월 1일부터 10,000,000원으로 증액한 계정

| 시드 이력 | 적용 시작일 | 시드 금액 |
|---|---|---|
| 1 | 2026-01-01 | 5,000,000 |
| 2 | 2026-07-01 | 10,000,000 |

1월\~12월을 조회하면 한 줄이 아니라 두 줄로 표시된다.

| 구간 | 적용 시드 | 순수익 합계 | 수익률 |
|---|---|---|---|
| 2026-01-01 \~ 2026-06-30 | 5,000,000 | 500,000 | 10.00% |
| 2026-07-01 \~ 2026-12-31 | 10,000,000 | 500,000 | 5.00% |

7월에 시드를 늘려도 상반기 수익률은 5,000,000원 기준의 10.00%로 남는다.

**통합 수익률 예시** — 계정 A·B를 운용하다가 B를 2026-03-31에 비활성 처리한 경우. 조회 구간은 2026-01-01 \~ 2026-04-30

| 계정 | 기준 시드 | 적용 시작일 | 비활성일자 |
|---|---|---|---|
| A | 10,000.00 | 2026-01-01 | — |
| B | 5,000.00 | 2026-01-01 | 2026-03-31 |

유효 시드 합계가 바뀌는 날짜는 2026-04-01 하나이므로 두 구간으로 나뉜다.

| 구간 | 유효 시드 합계 | 순수익 합계 | 구간 수익률 |
|---|---|---|---|
| 2026-01-01 \~ 2026-03-31 | 15,000.00 | 1,500.00 | 10.00% |
| 2026-04-01 \~ 2026-04-30 | 10,000.00 | 300.00 | 3.00% |
| 통합 수익률 | — | 1,800.00 | 13.00% |

분모를 현재 활성 계정의 시드 합계로 잡으면 B의 5,000.00이 빠져 1,800.00 ÷ 10,000.00 = 18.00%가 된다. B가 1\~3월에 올린 순수익은 분자에 그대로 남아 있으므로 실제보다 부풀려진 값이다.

**금액 입력 예시** — 총수익 $1,234.56 입력 시
- 수수료 입력란 기본 제안값 = 1,234.56 × 0.2 = 246.912 → 버림 → **$246.91**
- 사용자가 정산 내역의 실제 수수료 **$246.90**으로 고쳐 입력
- 저장되는 순수익 = 1,234.56 − 246.90 = **$987.66**

### 4.3 데이터 무결성 규칙

| ID | 규칙 |
|---|---|
| VAL-01 | 총수익은 0보다 커야 한다. 0과 음수는 입력 오류로 처리한다 (CON-08) |
| VAL-02 | 수수료는 0 이상 총수익 미만이어야 한다. 총수익 이상을 입력하면 순수익이 0 또는 음수가 되므로 입력 오류로 처리한다 (CON-08) |
| VAL-03 | 정산일자는 오늘 이전(당일 포함)만 허용한다 |
| VAL-04 | 계정명은 1자 이상 30자 이하로 제한한다 |
| VAL-05 | 메모는 200자 이하로 제한한다 |
| VAL-06 | 비활성 계정에는 신규 정산 기록을 등록할 수 없다 |
| VAL-07 | 시드 금액은 0보다 커야 한다. 0 입력을 허용하지 않아 수익률 계산 시 0으로 나누는 상황을 원천 차단한다 |
| VAL-09 | 동일 계정 내에서 적용 시작일이 같은 시드 이력은 2건 이상 존재할 수 없다 |
| VAL-10 | 모든 정산 기록은 적용 가능한 시드 이력을 반드시 가져야 한다. 계정의 가장 이른 시드 적용 시작일보다 앞선 날짜로는 정산 기록을 등록할 수 없고, 그런 기록이 이미 있으면 첫 시드 이력의 적용 시작일을 그보다 늦게 변경할 수 없다 |
| VAL-11 | 계정마다 시드 이력이 최소 1건 존재해야 한다 |
| VAL-12 | 시드 이력의 적용 시작일은 오늘까지(당일 포함)만 허용하고, 비활성 계정은 비활성일자까지(당일 포함)만 허용한다. 비활성일자 이후의 시드는 어떤 수익률 계산에도 쓰이지 않기 때문이다. 오늘의 판정은 CON-11의 기준 시간대를 따른다 |
| VAL-13 | 소수 2자리를 초과하는 금액 입력은 거부한다. 화면에 보이지 않는 자리가 저장되어 합계가 어긋나는 것을 막는다 |
| VAL-08 | 정산 기록 조회 시 수수료와 순수익은 기록에 저장된 값을 그대로 사용한다. 계정의 기본 수수료율을 참조해 조회 시점에 재계산하지 않는다 |

저장소의 docs가 원본이며, 다른 곳에 있는 사본보다 우선한다.
단, 화면 설계서에는 원본이 Design 캔버스라고 적혀 있다([screens.md](design/screens.md) 12행).

## 문서 간 기준

각 문서에 적힌 규칙을 그대로 옮겼다. 요구사항명세서와 화면 설계서에는 문서 간 우선순위 규칙이 없다.

| 문서 | 적힌 규칙 |
| --- | --- |
| 프로젝트 기획서 | 기능·데이터·계산 규칙의 상세 정의는 요구사항명세서(이하 SRS)가 기준이며, 두 문서가 어긋나면 SRS를 따른다. 기술 스택과 배포·운영 구성은 시스템 아키텍처 설계서(이하 설계서)가 정한다. |
| 시스템 아키텍처 설계서 | 무엇을 만들지는 SRS가, 언제·어떻게 오픈·운영할지는 기획서가 기준이다. 세 문서가 어긋나면 SRS, 기획서, 이 문서 순으로 따르고 이 문서를 고친다. |
| DB 설계서 | 무엇을 저장할지는 SRS 4장이, 어떤 DB와 구조로 저장할지는 설계서 6장이 정하고, 이 문서는 그 결정을 실행할 수 있는 스키마로 옮긴다. 문서가 서로 어긋나면 SRS, 기획서, 설계서, 이 문서 순으로 따른다. |
| API 명세서 | 경로, 파라미터, 요청과 응답 필드, 상태 코드, 오류 코드는 이 문서가 기준이다. 무엇을 만들지는 요구사항명세서(이하 SRS)가, 어떤 구성으로 만들지는 시스템 아키텍처 설계서(이하 설계서)가 정한다. 문서가 어긋나면 SRS, 설계서, 이 문서 순으로 따르고 이 문서를 고친다. |
| 테스트 계획 및 시나리오 | 기대 결과는 요구사항명세서(이하 SRS)를 기준으로 쓴다. 이 문서와 SRS가 어긋나면 SRS를 따르고 이 문서를 고친다. |
| 배포 및 운영 문서 | 무엇으로 구성할지는 설계서가 정하며, 문서끼리 어긋나면 SRS, 기획서, 설계서, 이 문서 순으로 따르고 이 문서를 고친다. |

## 목적별 읽는 순서

| 목적 | 읽을 문서와 장 |
| --- | --- |
| 처음 볼 때 | 기획서 1\~4장 → 요구사항명세서 1\~2장 → 설계서 1\~3장 |
| 백엔드 구현 | 요구사항명세서 3\~4장 → 설계서 2장, 5\~9장, 11장 → DB 설계서 2장, 5\~8장 → API 명세서 2\~6장 |
| 화면 구현 | 요구사항명세서 6장 → 화면 설계서 "개요", "디자인 기준"과 화면별 절(장 번호 없음) → 설계서 10장 → API 명세서 2\~3장 |
| 테스트 작성 | 테스트 계획 3\~5장, 8\~9장 → 설계서 14장 → 요구사항명세서 4.2 |
| 배포와 운영 | 배포 및 운영 문서 1\~11장 → 설계서 12\~13장 → DB 설계서 8.2, 8.4 → 기획서 7장 |

## 문서 갱신 규칙

- 설계를 바꾸면 코드와 같은 커밋에서 문서도 고친다.
- 고친 문서는 버전과 변경 이력을 올리고, 그 버전을 참조하는 다른 문서도 함께 맞춘다.
- 파일 이름은 영문, 문서 제목은 한글로 둔다.
- 다이어그램과 화면 그림은 같은 폴더의 images/에 두거나 Mermaid로 쓴다.
